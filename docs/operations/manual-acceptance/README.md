# Глубокая проверка Mind Diary

[Requirements — требования владельца](Requirements.md) — исходные требования
из разговора. Менять их можно только с явного согласования владельца.
Остальные документы описывают способы реализации, а не новые требования от его имени.

[Проектные решения](design.md) — отдельно выбранные исполнителем организация,
порядок работы и пояснения; они не входят в Requirements.

Короткое имя базы: **«Глубокая проверка Mind Diary»**. «Добавь в глубокую
проверку» означает обновить этот каталог; «проведи глубокую проверку» —
выполнить согласованный набор по [порядку полного прогона](deep-review.md).
Путь manual-acceptance сохранён: здесь ручная работа человека или агента,
включая ревью кода и эксплуатации, а не исполняемый набор автотестов.

Каталог создан 2026-09-21 по запросу владельца. Это сценарии для человека или
агента, который последовательно работает с настоящим продуктом и оценивает
результат. Карточки не являются исполняемыми автотестами и не включены в CI,
`npm run check` или `acceptance:run`. Для UAT обязательны выбранные по меткам случаи.
Ни один сценарий при создании каталога не запускался.

## Как пользоваться

[Проверка организации и подбора](verification.md) — выполненные проверки
самого каталога и ограничения выбора по темам.

Для релиза использовать [UAT-подмножество](uat-selection.md): frontmatter
`uat` и условия выбирают нужные карточки, не весь каталог.

1. Прочитать [общие правила](defaults.md) и выбрать весь каталог или разделы.
2. Для глубокого прогона зафиксировать список ID и версии карточек на старте.
   «Все» означает все выбранные карточки с явным результатом для каждой,
   включая blocked; это не обещание, что всё прошло.
3. Прочитать README выбранного раздела: там общие данные, влияние и источник
   ожиданий. Затем идти по отдельным карточкам.
4. Результаты хранить отдельно по [порядку ведения истории](runs/README.md).
   [Шаблон карточки](templates/case.md) и [шаблон прогона](templates/run.md)
   не входят в набор проверок.

Ожидания основаны на связанных спецификациях; наличие карточки не подтверждает
реализацию или доступность функции на выбранной версии. Отсутствующая
обязательная функция — defect; функция вне согласованного scope — not-applicable
с основанием; нехватка доступа или данных — blocked.

## Границы и развитие

[Развитие по найденным багам](maintenance.md) задаёт постоянный рабочий порядок.
[Карта переноса](sources.md) связывает прежние документы с карточками и
объясняет, какие исторические и автоматические материалы сохранены отдельно.

Это начальный набор, не заявление о полном покрытии продукта. Нет отдельной
полной матрицы устройств, ёмкости, account deletion,
provider outage и длительной нагрузки. Добавлять их по конкретному риску,
не умножая автоматически все сценарии на все клиенты и размеры.

Новый воспроизведённый пользовательский дефект добавляет короткий регрессионный
случай. Общие шаги переиспользуются ссылкой, ID не меняется при переименовании.
Новый случай не расширяет уже идущий прогон без явного изменения его scope.

Ручной план [релизного профиля](../ship-work-release-profile.md) использует
этот каталог. Автоматические suites, runtime и deployment не изменены.
