# Общие правила ручной приёмки

## Минимум и наследование

Обычная карточка: стабильный ID в заголовке, название, необходимые данные,
шаги и ожидаемый результат. Раздел задаёт группу, затрагиваемые части и общую
подготовку. Остальные поля добавляются только при отклонении от defaults.

Приоритет: эти правила → README раздела → конкретная карточка.
Например, строка `Лимит: 25 минут.` заменяет общий лимит; остальные правила
сохраняются. Не добавлять пустые поля или копии дефолтов.

## Время и остановка

- По умолчанию 10 минут на карточку: её специальная подготовка, действия и
  проверка результата. Общая подготовка раздела учитывается отдельно и тоже
  ограничена 10 минутами, если заранее не выбран иной лимит.
- Лимит — предел работы, а не SLA продукта и не оценка нормальной задержки.
  Зависший пользовательский экран фиксировать как наблюдение сразу.
- По истечении времени записать timeout, последний шаг и состояние операции.
  Не продлевать лимит молча и не начинать полный отсчёт заново после перерыва.
- Нет автоматических повторов. Новый запуск имеет отдельную запись и причину:
  исправление, восстановленный prerequisite или проверка конкретной гипотезы.
- Ожидание отдельного инструмента должно позволять вернуться к контролю до
  общего deadline. Markdown сам не обеспечивает принудительную остановку:
  исполнитель ведёт таймер и выбирает ограниченные ожидания.
- Остановка ожидания не отменяет серверную операцию. Проверить её статус,
  безопасно отменить при возможности и выполнить очистку. Очистку учитывать
  отдельно; при невозможности завершить записать cleanup pending и объекты
  для продолжения. Не идти к зависимым действиям с неизвестным состоянием.

Независимые карточки продолжаются после дефекта или timeout. Диагностика и
исправление — отдельная работа; они не поглощают прогон. Успех после повтора
не стирает первоначальную неудачу.

Исключение: раскрытие чужих данных, потеря/повреждение данных либо непонятная
граница изоляции останавливают все потенциально затронутые мутации. Сохранить
безопасное наблюдение и выполнить разрешённые действия по локализации;
продолжать независимые проверки только когда их изоляция подтверждена.

## Среда, данные и полномочия

Среда и клиент задаются один раз на прогон; default — изолированные тестовые
данные в UAT. Перед запуском сверить актуальный target по
[профилю доставки](../ship-work-release-profile.md). Production не подразумевается.
Во время чужого релиза не менять общий deployment, настройки или credentials;
при смене версии посреди прогона остановить зависимую группу и разделить результаты
по фактическим версиям.

Любая запись — только в run-owned ordinary Mind изолированного тестового
principal. Personal write — только disposable principal в изолированной
acceptance environment с разрешённым lifecycle. Если его нет — blocked.
Пользовательские Minds не являются тестовыми; чтение возможно лишь в пределах
запроса и прав, запись и cleanup таких Minds запрещены.

Перед подготовкой сохранить полную baseline inventory; пометить создаваемые
объекты run ID. В конце удалить только созданное этим прогоном и сверить baseline.
Следовать полному правилу изоляции в релизном профиле, не упрощать его этой памяткой.
Публикация синтетического Mind, роли, OAuth и разрушительные сценарии выполняются
только при соответствующих полномочиях. Карточка сама их не выдаёт.

Использовать встроенный Browser; другое средство — по актуальной browser policy.
Не менять рабочее подключение пользователя ради тестовых мутаций.
Исключение — прямо разрешённое обновление metadata/instructions существующего
подключения по CHATGPT-03 с сохранением прав и прочих настроек.
Не запускать
`acceptance:run` вместо ручных шагов. Допустимы read-only инструменты для
проверки hashes, состава архива и сохранённых данных; это не заменяет journey.

## Результат и влияние

Статусы: passed, defect, blocked, timeout, not-run, not-applicable.
Default до выполнения — not-run. Passed требует наблюдения ожидаемого результата
и завершённой применимой очистки; до неё функциональный успех отмечается отдельно.
Скриншот успешной кнопки не подтверждает сохранность данных.

Влияние дефекта определяется фактом: потеря/раскрытие данных; блокировка основного
сценария; частичная поломка; неудобство. Карточка может уточнить риск, но не
обязана заранее назначать severity. Теги затрагиваемых частей раздела помогают
выбирать проверки; они не доказывают достаточность покрытия любого diff.

Без приватного content, credentials, подписанных URL и личных инструкций в Git.
Публичный результат содержит безопасное наблюдение и ссылку на разрешённое
свидетельство. Исходные приватные материалы остаются в разрешённом закрытом месте.
