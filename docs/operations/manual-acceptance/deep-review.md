# Порядок глубокой проверки

Без дополнительного сужения глубокая проверка охватывает пользовательские
сценарии, весь репозиторий, эксплуатацию/MCP и отдельно ChatGPT и Codex.
Это управляемое ручное исследование; автоматические suites остаются отдельными.
При создании этого порядка ни код-ревью, ни интеграционные проверки не выполнялись.

## Подготовка и бюджет

Зафиксировать версии каталога, репозитория, deployment, клиентов и выбранные ID.
Список составных проверок развернуть в уникальные пары ID + клиент/среда/данные:
общие шаги не дублировать, а разные клиенты не объединять одним pass.
Установить общий временной бюджет до запуска с учётом числа карточек и частей
ревью; при отсутствии явного бюджета предложить оценку и фиксировать выбранный
предел, а не запускать неограниченный цикл. Лимит 10 минут не является оценкой
длительности всего репозитория.

Когда общий бюджет исчерпан, сохранить покрытие и точку продолжения.
Полный просмотр не объявлять завершённым, если остались файлы или случаи.
Независимые проверки продолжать в пределах бюджета при обычных failures;
границы безопасности из defaults имеют приоритет.

## Ревью всего репозитория без гигантской карточки

1. На закреплённом SHA получить список отслеживаемых файлов. Включить packages,
   apps, scripts, .github, конфигурацию, dependency manifests/lockfiles, тесты
   и продуктовые/операционные документы. Не ограничиваться последним diff.
2. Разбить исходники на небольшие связанные участки по подсистемам, сохранив
   вызовы между слоями. Для каждого участка применить относящиеся направления
   REVIEW-01…05. Одна рабочая порция по умолчанию ограничена 10 минутами.
   Не создавать постоянную карточку на каждый исходный файл.
3. В отчёте вести компактный список: путь/диапазон, применённые направления,
   просмотрено/частично/не просмотрено, находки или оставшийся вопрос.
   При timeout сохранить точное место остановки; продолжение — новая порция
   с учётом уже потраченного общего времени, а не повтор с начала.
4. Для generated/vendor/binary и других непросматриваемых построчно файлов
   указать основание и альтернативу: генератор, lock integrity, asset metadata.
   README-декларация сама не подтверждает корректность кода. Размер файла не
   является основанием молча исключить его.
5. Завершить отдельным проходом сквозных связей: identity → authorization →
   storage, commit → index, import/export → jobs/cleanup, build → artifact →
   deployment → client catalog. Локально хорошие функции могут плохо работать вместе.

«Ревью всего репозитория завершено» означает учёт каждого файла и завершение
применимого анализа или явно обоснованного исключения. Это не доказательство
отсутствия всех багов. Документы проверяются на согласованность с текущей
реализацией; предложение или отложенный scope не объявляется недоделкой без основания.

## Находки и дальнейшие действия

Находка содержит путь и строки на выбранном SHA, конкретный сценарий отказа,
влияние, факт или гипотезу и способ проверки. Для performance указывать
причину роста работы и размер данных; без измерения не выдумывать p95.
Стиль и предпочтение архитектуры не выдавать за подтверждённый дефект.

Подтверждённый продуктовый баг пополняет каталог по [правилу развития](maintenance.md).
Для статически найденного дефекта карточка может оставаться not-run.
Гипотезу можно сохранить как исследовательский случай с явно неизвестным
условием воспроизведения. Исправления, deployment и нагрузочные эксперименты
не выполняются автоматически как побочный эффект ревью.

## DevOps и независимые клиенты

OPS проверяет цепочку поставки, фактический MCP transport, диагностику и
изолированное восстановление. Проверка rollback-плана не означает выполненный
rollback; backup одного Mind не означает backup сервиса.

ChatGPT и Codex имеют отдельные результаты подключения, metadata, OAuth,
выбора tools, файлов и поведения агента. Тест одного не доказывает другой.
Внутри Codex различать Desktop/CLI, а внутри ChatGPT — конкретную проверенную
поверхность. Не умножать остальные случаи на все варианты автоматически:
выбранные поддерживаемые сочетания указать в плане.

Доступ к настоящему аккаунту, новый consent, внешние настройки и restore
требуют соответствующих полномочий. Если предпосылки отсутствуют — blocked,
не подмена локальной заглушкой. Общий релиз другой сессии не останавливать,
не перезапускать и не менять для удобства проверки.

## Итог

Отдельно показать: результаты пользовательских случаев; покрытие ревью файлов;
DevOps/MCP; ChatGPT; Codex. Затем — дефекты по влиянию, неизвестное,
время/доступный измеренный расход, cleanup и оставшийся объём.
Общий зелёный результат невозможен при скрытых blocked/timeout/not-run.
