# Развитие каталога вместе с проектом

При обнаружении или исправлении продуктового дефекта агент обновляет каталог
в рамках той же работы, без отдельного напоминания пользователя. Это правило
процесса, а не фоновый сервис: постоянный мониторинг и автоматический запуск
тестов не создаются.

1. Найти похожую карточку по действию пользователя и группе. Если она уже
   покрывает сбой, добавить ссылку на известный дефект и недостающее условие,
   а не создавать дубль.
2. Если случая нет — создать отдельную короткую карточку в подходящем разделе,
   указать источник обнаружения и добавить ссылку в README раздела.
   Для UAT поставить `uat` и условие `uat_when` по
   [правилам выбора](uat-selection.md); не копировать шаги в релизный отчёт.
   Указать точные topics из словаря; проверить подбор selector и отсутствие
   ненужных соседних сценариев. Запуск selector не запускает сам случай.
   Раздел regressions нужен для ещё не классифицированных инцидентов;
   исправленные случаи остаются в каталоге, даже если баг закрыт.
3. Записать именно путь пользователя, существенные данные и наблюдаемый
   результат. Проверка отдельного исправленного метода его не заменяет.
   Если воспроизведение неизвестно — перечислить недостающие условия;
   при запуске такой случай blocked, а не неявно пропущен.
4. При исправлении связать существующую задачу/отчёт с ID случая. Выполнить
   ручную проверку только в разрешённом объёме; при запрете запуска сохранить
   not-run и не заявлять, что баг подтверждённо устранён для пользователя.
5. После разрешённой проверки сохранить результат, время и безопасные
   свидетельства в истории. Обновить агрегированную оценку по наблюдениям.

Автотест, добавленный на тот же баг, остаётся в tests/ и может быть ссылкой
в карточке; он не заменяет результат ручного сценария. Новая задача в Task
Manager автоматически этим правилом не создаётся.

Изменение поведения продукта требует сверить связанные группы каталога.
Существенно изменившуюся карточку версионирует Git; прежние прогоны сохраняют
свой снимок. Удалять историю или переписывать старый fail в pass нельзя.
Устаревшую карточку исключать с причиной и ссылкой на замену, сохраняя ID в Git.

При срочном устранении инцидента сначала восстановить безопасную работу;
обновление каталога выполнить перед итоговым завершением разрешённой задачи.
Не расширять scope текущего прогона бесконечно из-за новых находок.
